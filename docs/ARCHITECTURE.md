# JetLog — Architecture

**This file is the single source of truth for how JetLog is built.** It is written from the code, and where it and any other doc disagree, the code wins and this file is what gets fixed.

> **Maintenance contract (read before editing the system).**
> Update this file **in the paired commit** (`/commit`: the code in jetlog, this file in jetlog-ops, same branch and message) for any change that touches one of its subjects:
> the **module dependency rules**, the **request lifecycle**, the **data model or its invariants**, the **API contract**, the **client state model**, or the **extension points**.
> A routine feature that only follows the existing patterns (a new rule column, a bug fix, a copy tweak) does **not** need an edit here. A structural change (a new table, endpoint, layer, store slice, or a changed invariant) does. Keeping this current is what keeps it trustworthy — a stale architecture doc is worse than none.

JetLog is IsraJet's lounge-entry system: scan a boarding pass → parse BCBP → match an entry rule → handle guests → log the movement → show the result. It began as a POC and is now the production application. `docs/PLAN.md` holds the current plan and `docs/DECISIONS.md` the decisions in force; `docs/archive/POC_Architecture.md` and `docs/archive/POC_PHASES.md` are historical (the latter's decision log stays live).

---

## 1. The stack

- **`server/`** — Node + Express + TypeScript (ESM, strict). Drizzle ORM → PostgreSQL. Vitest + supertest.
- **`client/`** — Vite + React 18 + TypeScript. One Zustand store. Tailwind v4 + shadcn/ui (`components/ui/`) alongside the older plain CSS (`styles.css`, the POC screens, replaced screen by screen). **One set of design tokens** in `src/index.css`, under shadcn's names, light (`:root`) and dark (`.dark`), read by both. Fonts (Rubik, IBM Plex Mono) are bundled npm packages, so the on-prem machines need no internet.
- Dev: client on port 3000 proxies `/api` to the server on 8000. Input is the USB scanner (keyboard wedge) only.

## 2. The request lifecycle (one scan, end to end)

```
[ScanStage]  raw BCBP string from the USB scanner → the main scan box (or the open modal's
   │            scan field — useWedgeRouting keeps the scan in one), Enter submits
   │  primary scan: api.getClubOptions(raw) → POST /api/scan/club-options (logs nothing)
   │     clubs offered → the flow modal's club step (mode 'club') → the operator picks one, or None
   │  api.scan(rawBarcode, loungeId, hostEntryId?, clubId?)  → POST /api/scan  { rawBarcode, loungeId, hostEntryId?, clubId? }
   │  (loungeId = the station's lounge id from the store; no lounge picked → nothing is posted;
   │   guest scans never ask for a club)
   ▼
[routes/scan]         wires the path to the controller
[controllers/scan]    HTTP only: validate body shape, 400 on bad input; call the service; 201 + envelope
[services/scanService.processScan]   the spine:
   ├─ loungesService.assertActiveLounge   unknown/inactive lounge → 400, before anything is logged
   ├─ domain/parseBoardingPass   bcbp.decode → firstLeg (leg 1 only); judges nothing
   ├─ domain/uniqKey             ordinalDate-carrier-flightNumber-sequenceNumber-origin
   │  EVERY check runs — nothing short-circuits:
   ├─ globalRulesService + domain/globalRules.checkGlobalRules   every scan, guests too:
   │                              departure airport allowed? flight date within the window around today
   │                              (Israel)? → every rule it fails
   ├─ dedup                      an already-APPROVED entry with the same uniq_key → ALREADY_ENTERED
   ├─ club (optional clubId)     must be a club the picker would offer (below), else 400; never on a guest
   ├─ rulesService.getActiveRules + domain/ruleKey.matchRule   wildcard-collapse each dimension → ruleKey → active rule
   │                              the station's own lounge rules first, then the all-lounges ones (lounge '#');
   │                              keys spell ids: carrier-compartment-ff-companyVar-<club id|#>-<lounge id|#>
   ├─ guest path (when hostEntryId set)   host's snapshotted guest_policy: ANY | SAME_CARRIER | SAME_FLIGHT
   ├─ domain/denyReasons.collectDenyReasons   every failure, in the pinned order; empty = approved
   ├─ ruleAtScanTime             the matched rule as it reads now (readable key, description, comments);
   │                              all null — and no rule_key — when no rule matched, and on every guest
   └─ insert                     EVERY scan is written to `entries`, approved or denied, with its `deny_reasons`
   ▼
[PostgreSQL]  rules (policy, 231 seeded) · entries (the movements log, each tagged with its lounge)
   ▼  { success: true, data: ScanResponse }
[api/client]  unwraps the envelope → plain data (or throws Error)
[store]  applies the result → mode 'result'; the flow modal shows APPROVED/DENIED (ResultCard)
         with its own "Scan the next passenger" field; refreshEntries()
```

Two side paths share the same shape:
- **Exceptional approval** — `POST /api/scan/exception` (`exceptionApprovalService`): a human admits a passenger when the scan failed or there is no barcode. Always approved, never deduped (`uniq_key` null); the station's `lounge` and the approver name are validated against their ACTIVE tables, and notes are optional context (may be null). A group admitted by exception is **one entry with a `quantity`** (1 to the `max_exception_quantity` global rule, default 1); it has no guests (`allowed_guests` 0).
- **Re-entry** — `POST /api/scan/reentry` (`exceptionApprovalService.processReentry`): lets a pass that **already entered** back into the lounge (e.g. a flight delay), as many times as needed. A kind of exceptional approval: approved, `is_exceptional`, approver validated, no guests, `quantity` 1. It **requires a readable barcode** and guards that an approved admission for the pass's `uniq_key` already exists (else 400), then logs a new entry that **keeps that `uniq_key`** and sets `is_reentry` (so it's excluded from dedup — see the dedup invariant). A re-entry never modifies the original entry; both stay in the log, tied by the key.
- **Modifying an entry in place** — `POST /api/entries/:id/{move,rescan,exception,void,quantity}` (+ `move/club-options`, `rescan/club-options`) (`entryModificationService`). Each loads the entry and asks the pure `domain/entryModification.modificationProblem` whether the change is allowed now (the modify window, a voided entry, the action's own condition → 409 with the reason). A move and a rescan re-run the scan checks through `scanService.evaluatePass` — the same function a new scan uses — with dedup ignoring the entry itself, then update the row in place and set `modified_at`. A move re-checks the host's guests against its new snapshot (`recheckGuests`). `GET /api/entries/:id` returns one entry's group (a host with its guests).
- **The log and the export** — `GET /api/entries` and `GET /api/entries/export` (`entriesService`) read the same filters, parsed and validated by the pure `domain/entryFilters.parseEntryFilters` (400 naming the bad parameter). The service turns them into SQL conditions on one row and selects whole **parties** (a host and its guests) with at least one member matching every filter. The log returns one **page** of those parties' hosts — `ENTRIES_PAGE_HOSTS` (100), newest first, after an opaque `cursor` (keyset on the hosts' `(created_at, id)`, made and checked by the pure `domain/entriesPaging.ts` — a cursor that isn't one it made, including one naming a moment that doesn't exist, is a 400; it carries the database's microsecond timestamp, which a JS `Date` would truncate) — with **all** their guests nested, each row carrying `matchesFilters`, plus `nextCursor` and, on the first page, `totalHosts`. The export counts its rows first, in one query (an over-cap export is refused before anything else is read or a byte is sent), then **streams**: it takes the matching party ids once — one number per party, a few MB at the cap, the only part of memory that grows with the export — reads the rows 2,000 parties at a time, and writes each batch with the pure `domain/entriesCsv.entriesCsvRows` after `entriesCsvHeader` — every entry of those parties, or with `match=entry` only the matching ones, one CSV row each — so rows never pile up (≈40 MB live heap at the peak for 400,000 rows). A failure mid-stream aborts the download rather than ending the file early. Both reuse the read context (current codes, `ruleKeyReadable`).
- **Club options** — `POST /api/scan/club-options` (`scanService.getClubOptions`): "ask first, log once". Parses the pass and logs **nothing**; returns the clubs the operator may pick at the station's lounge (`domain/ruleKey.clubOptions` over that lounge's rules and the all-lounges ones, ∩ ACTIVE clubs, in rule/Excel order). It takes the station's `loungeId` (required), since each lounge has its own rules. **The club comes last**: the picker is offered only when every other check passes (in this pre-check, a pass with club options counts the rule check as passed). Otherwise it returns none, and the client posts the scan without a club, which logs the denial with all its reasons. The client then posts one scan with the pick as `clubId`; only a club the picker would offer is accepted.
- **Rules editor** — `GET/POST /api/rules`, `PATCH /api/rules/:id` (`rulesService`): CRUD over the rules table; `POST /api/rules/bulk-active` and `/bulk-delete` act on a selection, all or nothing.
- **Rules CSV import** — `POST /api/rules/import/preview` then `POST /api/rules/import` (`rulesImportService`): the client posts the export's CSV text and a target lounge (`null` = all lounges). `domain/rulesCsv.parseRulesCsv` reads it and `planRulesImport` sorts every row into added / reactivated / skipped / inactive-in-file / invalid; the preview saves nothing, and the commit plans again inside one transaction that locks `rules`, then saves every row or none.
- **Clubs admin** — `GET/POST /api/clubs`, `PATCH /api/clubs/:id`, and `PUT/DELETE/GET /api/clubs/:id/image` (`clubsService`).
- **Global rules admin** — `GET /api/global-rules`, `PATCH /api/global-rules/:key` (`globalRulesService`): edit the values of the fixed keys.
- **Approvers / lounges admin** — `GET/POST /api/approvers`, `PATCH /api/approvers/:id` (`approversService`) and the same shape for `/api/lounges` (`loungesService`).

Controllers are plain `async` handlers. The server runs on **Express 5**, which forwards a rejected promise (a thrown `ErrorResponse`, a `BoardingPassParseError`, anything) straight to the error pipeline — no `asyncHandler` wrapper needed. The central `errorHandler` (registered last, after `notFound`) turns any error into `{ success: false, error }`: an `ErrorResponse` carries its `statusCode`; a `BoardingPassParseError` maps to 400; anything else is 500.

## 3. Module dependency rules (what may import what)

### Server (`server/src/`)

```
routes/ ──▶ controllers/ ──▶ services/ ──▶ domain/   (pure, no I/O)
                                  │
                                  ▼
                                 db/    (Drizzle: schema, client, migrations, seed)
```

| Layer | Owns | May import | Must NOT import |
|---|---|---|---|
| `routes/` | Wiring path → handler | controllers | services, db, domain |
| `controllers/` | HTTP: validate body shape, call one service, return the envelope. Each keeps the `@desc/@route/@access` header. | services, `types/`, `utils/ErrorResponse` | db, domain directly |
| `services/` | Business rules + DB access; transactions live here | domain, db, other services, `types/` | controllers, routes |
| `domain/` | **Pure business logic, zero I/O** | other domain modules, `bcbp` | **db, services, controllers, express** |
| `db/` | The Drizzle model, lazy pool, migrations, seed | domain (types, and pure functions the seed needs — e.g. `ruleKeyFromDimensions`), config | services, controllers |
| `middleware/`, `utils/`, `config/`, `types/` | Envelope, error class, config, DTOs | — | — |

Hard rules:
- **`domain/` never imports `db/`** (or anything with I/O). It is what the unit tests exercise directly.
- **No SQL outside `db/` and `services/`.** Controllers never touch the DB.
- **`types/dto.ts` may import `domain/`** (e.g. the `GuestPolicy` type from `domain/types.ts`); the reverse — `domain/` importing `dto.ts` — is not allowed.
- The db client is **lazy** (`getDb()` builds the pool on first use), so importing a service does not force a DB connection; `GET /api/health` runs with no database.

### Client (`client/src/`)

```
lib/ (pure, React-free) ──▶ store/ (slices) ──▶ hooks/ ──▶ components/ ──▶ App.tsx
                                  │
                                  ▼
                               api/client.ts ──▶ (fetch, unwraps the envelope)
```

| Layer | Owns | Rule |
|---|---|---|
| `api/` | `client.ts` (fetch + unwrap `{success,data}`) · `types.ts` (hand-mirror of server DTOs) | Unwrap the envelope here, never in components. No hardcoded backend URLs. |
| `lib/` | Pure logic: `theme.ts` (the theme choice `system` \| `light` \| `dark` in `localStorage`, resolving it against the system setting, and putting the `light`/`dark` class on `<html>`), `language.ts` (the language `he` \| `en` in `localStorage`, Hebrew by default, and putting `lang` on `<html>`), `scannerLayout.ts` (the character a US keyboard types for a physical key, so a scan field undoes a Hebrew layout), `message.ts` (a `Message`: one of our catalog keys with its values, or the server's own words — what `lib/` and the store hold instead of text; `sameMessage`), `dates.ts` (the one date and time format of both languages, `03/10/2026 14:05`, 24-hour, this computer's time zone), `entriesView.ts` (single-entries + search narrowing, sort, group), `entryDays.ts` (the operator's log split into scan days, newest first, the sort kept inside each day, and each day's header as data: today / yesterday, the weekday, the date), `recentScans.ts` (the Recent strip's query — the station's lounge only — and its size, 6), `entryFilters.ts` (the filter values and the query string the log and the export share — mirrored from the server's `domain/entryFilters.ts`), `rulesCsv.ts` (the export, and the import/bulk limits checked before posting — mirrored from the server), `rulesSelection.ts` (the rules list's selection, select-all over the rows shown, the bulk-delete check, the import summary), `entryActions.ts` (which in-place change an entry allows now, and why not as a `Message` — mirrors the server's `modificationProblem`; ## 4. Data model (`server/src/db/schema.ts` is the model)

### `rules` — the policy (seeded from Vlad's Excel `Rules` sheet, 231 rows)
**The seed is provisional:** `server/src/db/seed-data/rules.json` — and the club codes `seedClubs` derives from it — is expected to change as Vlad reviews the rules. `db:seed` seeds an empty rules table and skips a non-empty one; replacing it needs `--force` (refused in production, and refused on a locked database whatever the flags — see `deployment_state` below), and a forced reseed drops rules added by hand in a dev database.

`carrier`, `compartment`, `frequent_flyer`, `company_var` (each `#` = wildcard), `club_id` (FK → `clubs.id`; **NULL = any club or none**, the `#` of the key), `lounge_id` (FK → `lounges.id`; **NULL = every lounge**, the `#` of the key — all seeded rules), derived `rule_key` (`carrier-compartment-ff-companyVar-<club id|#>-<lounge id|#>`, e.g. `EY-#-#-LA-7-#`; stored, computed when the rule is written, and spelling **ids**, so a club or lounge re-code never changes it — the API adds a `ruleKeyReadable` with the current codes, computed on every read and never stored), `description` and `comments` (optional free text, `varchar(2000)` — `RULE_TEXT_MAX_CHARS` in `domain/ruleFields.ts`, checked first with a clear 400), `allowed_guests` (int), `active`, `guest_policy` (`'ANY'` | `'SAME_CARRIER'` | `'SAME_FLIGHT'` — `NOT NULL DEFAULT 'ANY'`; `ANY` = no restriction, stored explicitly, not null).

### `entries` — the movements log (every scan attempt)
Parsed fields (`carrier`, `flight_number`, `flight_date`, `compartment`, `frequent_flyer` = FF airline designator, `frequent_flyer_number` = FF member number, `company_var`), `uniq_key`, `approved`, `rule_key` (the **matched** rule's key; null when none matched, on guests, and on a no-barcode exception — rows from before migration 0019 may hold the key a denied scan tried), the rule at scan time (`readable_rule_key_at_scan_time`, `rule_description_at_scan_time`, `rule_comments_at_scan_time` — see the invariant below), `is_guest`, `host_entry_id` (guest → host self-reference = **the billing proof**), `lounge_id` (FK → `lounges.id`, no default — the station's lounge, required on every insert), `club_id` (FK → `clubs.id`, the club the operator picked; **NULL = a club-less passenger** or no prompt), `guest_policy` (the policy snapshotted from the matched rule when a host is admitted — see the invariant below; null on guests, no-rule scans, and legacy rows), `deny_reasons` (`text[]` — every reason the scan was denied, in the pinned order of `domain/denyReasons.ts`; null = none recorded: an approved scan, or a row from before migration 0014), the exceptional-approval fields (`is_exceptional`, `is_reentry` — a re-entry of an already-admitted pass, always also `is_exceptional`; `approver_name`, `exception_notes`, `order_number`, `service_company`), `created_at`. `raw_barcode` and `uniq_key` are nullable (a no-barcode exceptional approval has neither).

### `approvers` — who may grant an exceptional (manual) approval
`id`, `name` (globally unique), `kind` (`'internal'` | `'external'`), `company` (the external company; null for internal), `active`. Replaces the old hardcoded `domain/approvers.ts` allowlist; the exceptional-approval flow validates `approver_name` against the ACTIVE rows here, and `approversService` exposes CRUD. Seeded (non-destructively) with the four internal managers by `seedApprovers` in `db/seed.ts`. **Guest policies are deliberately NOT a table** — they stay the closed string vocabulary in `domain/types.ts` (the behavior lives in `domain/guestPolicy.ts`); tabling them is deferred indefinitely (docs/DECISIONS.md).

### `clubs` — the loyalty levels an operator picks at scan time
`id`, `code` (unique, editable — e.g. `Gold`; one **global** row shared by every airline's rules), `description` (optional), `active`, `image` (`bytea` — the resized WebP the popup shows, ≤ 256 px, ~10–30 KB; stored in the row so `pg_dump` backs it up), `image_hash` (versions the image URL for caching). Migration `0010` seeds the 15 codes Vlad's rules use. The `Guest` "club" of the Excel is **retired**: it was the Excel's way of handling guests, which JetLog does with `is_guest` + `host_entry_id`; those 40 rules name no club and are inactive (never deleted).

### `lounges` — the physical lounges a station can be set to
`id`, `code` (unique, editable — the operator-facing identifier; lounges have no separate name), `description` (optional), `active`. `entries.lounge_id` references `id`, so changing a code touches only the lounge row; the entries list joins the current code for display. Migration `0008` seeds one lounge (`A`); the rest are managed from the lounges view (moving into the planned admin panel). **Rules can be per lounge**: a rule names one lounge, or none (all lounges).

### `global_rules` — scan rules for every scan in every lounge
`id`, `key` (unique), `value` (text), `updated_at`. One row per rule, its value a string: `departure_airports` (`TLV`, or several codes separated by commas), `max_days_before_departure` and `max_days_after_departure` (whole days, 1–366), `max_hours_to_modify_entry` (whole hours, 1–720 — the modify window) and `max_exception_quantity` (whole people, 1–10,000 — the most one exceptional approval may admit; the ceiling is `EXCEPTION_MAX_QUANTITY`); the last two are operator rules that scans never check. **Each key is wired to its own code** in `domain/globalRules.ts`, so a row is added only by the migration that ships with the code reading it (`0013` seeds the first three, `0017` the modify window, `0020` the exception quantity); the admin edits values, never keys. Values are validated per key on save and stored normalized (airports upper-cased and de-duplicated, numbers without leading zeros).

### `deployment_state` — the go-live lock
Exactly one row (`id = 1`, a CHECK forbids a second): `locked`, `locked_at`, `locked_by`. Migration `0011` creates the table and `0012` inserts the row **unlocked** (`locked = false`). `npm run db:lock -- --confirm <database name>` sets `locked = true` once, at go-live (`locked_by` = the OS user who ran it); there is deliberately **no unlock script** — unlocking is a manual SQL step in `docs/DEPLOY.md`. The lock lives in the database, not in an env var, because the operational commands run from a laptop through an SSH tunnel, where `NODE_ENV` is not `production`.

### Invariants
- **A locked database refuses every destructive script.** The decision is the pure `decideSeed` in `db/seedGuard.ts` (locked → refuse · empty rules → seed · no `--force` → skip, exit 0 · `NODE_ENV=production` → refuse even with `--force` · else replace). It runs twice: in the `db:seed` command before anything is written (so a refusal touches no table and exits 1), and inside `seedRules`' own transaction, which locks `rules` first — so a direct caller can't bypass it and two seeds can't interleave. `seedRules(db, { force })` makes every caller state whether it may replace a non-empty table. The integration tests pass `force: true` against their unlocked `jetlog_test`. The lock guards scripts, not an admin's deliberate actions in the app: the rules import, bulk (de)activation and the bulk delete of inactive rules all work on a locked database.
- **No two ACTIVE rules share a `rule_key`** — two would match the same scan ambiguously. **Enforced by the database**: the partial unique index `rules_one_active_per_rule_key` (on `rule_key WHERE active`, migration 0016). The services check first for a clear message, and turn the index's unique violation (23505) into the same 409 (`rulesService.guardActiveKey`), so a race between two writers can't get through. Inactive rules are exempt: they may share a key with an active rule or with each other.
- **Approver names are globally unique; approvers are deactivated, never hard-deleted.** Re-adding a removed name *reactivates* that row (`createApprover`) rather than making a duplicate. History is safe regardless: `entries.approver_name` is a text snapshot, not an FK.
- **Only inactive rules can be deleted.** A rule is deactivated first (matching ignores inactive rows), and only then may the admin delete it (`POST /api/rules/bulk-delete`); a selection holding an active rule is refused whole (409). No foreign key references `rules` (an entry keeps its own copy of the key and a snapshot of the guest policy), so deleting a rule leaves the log unchanged. Clubs and lounges are deactivated, never deleted.
- **The rules CSV import only adds.** A row's key is rebuilt from its columns and the **target** lounge the admin picked (the file's `id`, `rule_key` and lounge columns never decide; a file whose `lounge_id` column holds more than one value is refused). An ACTIVE rule with that key → the row is skipped; an INACTIVE rule with that key and the same description, comments, allowed guests and guest policy → that rule is reactivated (lowest id); otherwise the rule is added. Rows marked inactive in the file are not imported. `club_id` is the authority: it must exist, be active, and have the file's `club` code. Two rows that build one key, or any invalid row, abort the commit. Limits (mirrored in the client): a file ≤ 1 MB and ≤ 2,000 rules (`domain/rulesCsv.ts`); a bulk action ≤ 1,000 rules (`domain/rulesBulk.ts`).
- **Every entry names its lounge; only an ACTIVE lounge can log one.** Scans and exceptional approvals must carry `loungeId` (400 when missing or not a positive integer); `loungesService.assertActiveLounge` rejects an unknown or inactive id with 400 *before* anything is logged (the FK alone would only surface it as a 500). Lounges are deactivated, never hard-deleted (entries reference them); `code` is unique; re-adding a deactivated code reactivates that row.
- **Foreign keys reference ids, never codes.** Every FK points at the referenced table's surrogate `id`; codes are editable labels, joined for display. (A code is still unique, and still what a person types or sees.)
- **Global rules come first and fail closed.** Every scan — host or guest — is checked against `global_rules` before dedup, rule matching or the guest policy; each rule it fails is a deny reason of its own, reported with every other failure. An exceptional approval skips them, as it skips the rules. A missing row or an invalid stored value throws (500) rather than admitting every pass. The window counts **calendar days**, with inclusive edges, from **today in Israel** (`Asia/Jerusalem`): the barcode carries only a day of the year, so the flight is placed in last, this or next year — whichever is closest to today — which keeps the window right across New Year. (`bcbp`'s own year is used for the stored `flight_date` only; without an issuance date on the pass it takes the current UTC year.) A pass with no usable date is `FLIGHT_DATE_UNKNOWN`; one with no origin fails the airport check.
- **Every scan is logged**, approved or denied.
- **Every check runs; every reason is reported and stored** (this reversed the earlier rule "the deny reason lives in the response, not on the row"). Nothing short-circuits: a scan's reasons are every check it fails, in **one pinned order** (`DENY_REASON_ORDER` in `domain/denyReasons.ts`, held by a unit test): `DEPARTURE_AIRPORT_NOT_ALLOWED`, `FLIGHT_DATE_UNKNOWN`, `FLIGHT_TOO_FAR_AHEAD`, `FLIGHT_TOO_LONG_AGO`, `ALREADY_ENTERED`, `GUEST_CARRIER_MISMATCH`, `GUEST_FLIGHT_MISMATCH`, `GUEST_LIMIT_REACHED`, `NO_MATCHING_RULE`, `CLUB_REQUIRED`. They live in two places: the response (`reasons`, an array) and the row (`entries.deny_reasons`, a `text[]` — the same list). `approved` alone decides: approved = no reasons (stored as null). Guests get the global rules and the guest checks (a guest on another carrier under `SAME_FLIGHT` fails both), never `NO_MATCHING_RULE`. `FLIGHT_DATE_UNKNOWN` comes without the window reasons. `CLUB_REQUIRED` replaces `NO_MATCHING_RULE` only when the club is the sole failure (the pass has club options, None was picked, every other check passed), so it is always alone. The race loser adds `ALREADY_ENTERED` to its reasons. Bad requests (unknown/inactive lounge, a club that doesn't apply, a missing host, an unreadable barcode) are still rejected and log nothing. A denied row with null reasons predates migration 0014 ("reason not recorded"). An exceptional approval's own entry stores none.
- **Dedup key** = `ordinalDate-carrier-flightNumber-sequenceNumber-origin` (ordinalDate = ISO 8601 day-of-year, e.g. `007`). An already-approved entry with the same key → `ALREADY_ENTERED`. Exceptional entries have `uniq_key` null and never dedup. **Re-entries are the one exception that keeps a real key:** a re-entry (see the lifecycle note below) carries the pass's `uniq_key` but is flagged `is_reentry`, so it stays tied to the original admission for reporting while being deliberately let back in. **DB-enforced:** a partial unique index (`entries_one_approved_per_uniq_key`, on `uniq_key WHERE approved AND uniq_key IS NOT NULL AND is_reentry = false`) guarantees at most one approved, **non-re-entry** entry per key even under concurrent scans; `scanService.approvedEntryWithKey` (the dedup lookup) likewise ignores re-entries, so a plain second scan still denies with `ALREADY_ENTERED`. `scanService` keeps a pre-check as a fast path and converts the index's unique-violation (`23505`) into the same `ALREADY_ENTERED` denial. That index also serves the dedup lookup (an index seek, never a scan); a separate `entries_created_at_idx` serves the log's `ORDER BY created_at DESC` and the scan-date filter, `entries_host_entry_id_idx` serves every host → guests lookup (the log's nesting, the export's parties, and the guest → host foreign key's checks on delete), and `entries_flight_date_idx` serves the flight-date filter.
- **Filters select whole parties.** A host and its guests travel together: a filter matches a party when any member matches every filter, and the log and the export (by default) return the whole party — so a one-airline filter can bring a guest of another airline along. `matchesFilters` on each `EntryDto` says which rows matched themselves; `match=entry` makes the export strict (only those rows). The filter vocabulary is one module, `domain/entryFilters.ts`, mirrored by the client.
- **The export is refused, never cut short.** More than `ENTRIES_EXPORT_MAX_ROWS` (500,000 — about two years) matching rows → 400 "narrow the filters", before anything is streamed; a failure mid-stream aborts the download. The log is paged (100 hosts a page, whole parties), never capped.
- **Derivable from the barcode:** `compartment`, `companyVar` (EY's LA/LB/LC/LF, BA's `1`/`2`), and the FF **airline designator + member number**. **Not** in the barcode: the **club** — the operator picks it at scan time. No seeded rule uses the `frequentFlyer` dimension (all `#`), so the scan's FF designator always collapses to `#`.
- **A club is offered and accepted only where a rule uses it.** For a pass, the options are the clubs that — with that pass's other dimensions — build the key of an ACTIVE rule, and whose club row is ACTIVE (`clubOptions` ∩ active clubs). A picked club outside that set is a 400; so is a club on a guest scan. Rules reference clubs by id (`#` = NULL); entries keep the id.
- **`isValidBcbp` is virtual** — computed on read in `entriesService` (structural regex checks in `domain/validateBcbp`), never stored. Garbage scans are kept and hidden behind a UI chip, not rejected.
- **Rules per lounge: the station's own rules first, then the all-lounges ones.** `matchRule` builds the key over the station lounge's own active rules (wildcard-collapse over those rules only); if no rule matches, it tries the all-lounges rules (lounge `#`). So a lounge-specific rule always wins, and an all-lounges rule is a true fallback. (Collapsing the lounge like the other dimensions would let a lounge's own rules hide every all-lounges rule for that carrier.) A lounge where no active rule applies denies with `NO_MATCHING_RULE`. "No two ACTIVE rules share a key" holds with the lounge in the key, so the same rule may exist once per lounge and once for all lounges.
- **Rule keys spell ids; `ruleKeyReadable` spells codes.** `rules.rule_key` and `entries.rule_key` hold ids, so a club or lounge re-code rewrites nothing. `readableRuleKey()` (`domain/ruleKey.ts`) spells the key with the current codes on every read — rules, entries and the scan response. No part of a key may contain the separator `-` (the editor rejects it with a 400; a scanned value with `-` matches no rule and collapses to `#`). Entries logged before keys held ids keep their old key (e.g. `EY ##LAGold`), shown as it is.
- **Guests belong only to a host the rules admitted, up to its rule's allowance — snapshotted and enforced by the server.** When a host is admitted, `entries.allowed_guests` takes the matched rule's allowance. A guest scan needs an approved, unvoided host **not approved by exception**, inside the modify window, with a place left: places = allowance − its **approved** guests, so a denied guest holds none (`hostGuestsService.assertGuestPlace`; 409 for an exceptional host, 400 when no place is left, nothing logged). A row without the snapshot counts as 0. Every guest is checked by the rules; there are no exceptional guests, and a guest the rules refused can't be approved as an exception (it may come in as its own exceptional entry).
- **An exceptional entry carries a quantity; nothing else does.** `entries.quantity` (default 1) is how many people the entry admits: 1 to the `max_exception_quantity` global rule on a host approved by exception — a new one, "Approve anyway", or a move approved anyway — and always 1 on guests and on hosts the rules approved. **The range is enforced by the code only**, from the global rule on every endpoint that takes a quantity (the admin may set the rule from 1 to 10,000, `EXCEPTION_MAX_QUANTITY`); lowering it leaves existing quantities as they are. **The database enforces only who may have a quantity**: the check `entries_quantity_only_exceptional_host`. A host approved by exception stores `allowed_guests` 0, so it takes no guests; one that had guests before an exception-move keeps them as history. The log and its counts stay per entry; the export carries `quantity` for IsraJet's totals.
- **Entries are modified in place, inside the modify window.** `max_hours_to_modify_entry` (48) hours after `created_at` — never restarted — an entry can be moved (hosts; re-checked at the target, its guests move and are re-checked, a lower allowance denies the most recent extras with `GUEST_LIMIT_REACHED`; refused = nothing changes), rescanned (denied or garbage entries only — a guest only while its host has a free place, else it could only be denied again; any readable pass — the scanner may have misread the first — and dedup, ignoring the entry itself, still denies a pass admitted on another entry), approved as an exception (denied hosts, or a refused move — never a guest, and never a move of a host already approved by exception, whose move is never refused (409); it takes a quantity; the deny reasons stay as the record of what was overridden, and so does the dedup key; a moved host's guests move with it unchanged), given a new quantity (hosts approved by exception; no approver — the original stays), or voided (approved entries; with a reason and an approver; the host's guests too; the row stays, no longer approved). A voided entry takes no change. There is no audit trail: `modified_at` marks the last change.
- **The rule at scan time is stored, never recomputed** — a deliberate exception to "store ids, compute what people read": IsraJet wants an entry to read as it did at the desk. When a scan, a rescan or a move (`passColumns`), or a move approved anyway (`approveEntryAsException` with a lounge), decides an entry's rule, it writes `rule_key` and the three at-scan-time columns together, from the matched rule (`scanService.ruleAtScanTime`: the key spelled with the codes of that moment, the description, the comments). No matched rule → all four null; a guest is never matched against a rule, so all four are null on guests. A rule edit, deactivation or delete, or a club or lounge re-code, changes none of them; a plain in-place exception and a void keep them. The log's `ruleKeyReadable` is still computed with today's codes. Migration 0019 backfilled older rows from the then-ACTIVE rule with the same key (never guests) — a later reconstruction; the rest stay null.
- **Guest policy is snapshotted at admission.** When a host is approved, the matched rule's `guest_policy` is copied onto the host `entries` row; a guest is judged against that snapshot, not the rule's current value — so editing a rule mid-session cannot change an already-admitted host's guests. A host with no snapshot (null) defaults to the conservative `SAME_CARRIER`; only a host the rules admitted takes guests, and it always has one. `ANY` is a first-class policy value everywhere (`rules` and the snapshot), never null.

`0006` backfills `rules.guest_policy` null → `'ANY'` before its `SET NOT NULL`, and adds `entries.guest_policy`). `0005` adds the two `entries` indexes; `0007` adds the `approvers` table (approvers are seeded via `seedApprovers`, not the migration); **The entries filters** (`domain/entryFilters.ts`; AND between filters, comma-separated values within one mean any of them): `loungeId`, `clubId` (ids; `clubId` also `none`), `carrier`, `compartment`, `frequentFlyer` (designators, `none`, `any`), `flightDateFrom`/`flightDateTo` and `scanDateFrom`/`scanDateTo` (`YYYY-MM-DD`, inclusive; scan dates are Israel days), `status` (`approved`, `denied`, `voided`), `type` (`host`, `guest`), `exceptional`/`modified` (`true`/`false`), `denyReason` (codes; any of them), and `match` (`party`, the default, or `entry`). An unknown parameter is a 400.

Every entry modification answers 409 with the operator's reason when it isn't allowed now (the modify window, a voided entry, the action's own condition). `EntryChangeResult` = `{ applied, reasons, entry }` (the entry's group as it is now). `EntryDto` adds `quantity`, `allowedGuests`, `guestPlacesLeft` (computed), `hostGuestPlacesLeft` (on a guest, its host's places, computed; null on a host), `modifiedAt`, `modifiableUntil` (computed) and `voidedAt` / `voidReason` / `voidedBy`. `ScanResponse` adds, with `ALREADY_ENTERED`, `existingEntryId`. `ExceptionResponse` carries `quantity`, and `isReentry` when the approval was a re-entry. `EntryDto` carries `isReentry`, and the entries export a matching `is_reentry` column.

`ScanResponse` carries `approved`, `reasons` (`DenyReason[]`, every reason in the pinned order — see the invariant in §4; empty when approved), `ruleKey` + `ruleKeyReadable` (the matched rule's key and how it reads now — the value stored on the entry; both null when no rule matched, and on a guest), `clubId` + `club` (the picked club's id and code; null = none), `description`, `allowedGuests`, `entryId`, `isGuest`, optional `hostEntryId`, and a `parsed` block for display. `EntryDto` carries the stored `reasons` too (empty when none were recorded), `ruleKeyReadable`, the stored `readableRuleKeyAtScanTime` / `ruleDescriptionAtScanTime` / `ruleCommentsAtScanTime`, and `matchesFilters` (whether the row itself matched the log's filters; always true without filters). `RuleDto` carries `loungeId` + `lounge` (its code, `#` = all lounges), `ruleKeyReadable` and `comments`; `RuleInput` takes `loungeId` (null = all lounges) and an optional `comments`. The rules CSV has a `comments` column after `description`; the import reads it when present (a file without it imports with no comments), and an inactive rule is reactivated only when its description, comments, allowed guests and guest policy all match the row. `RulesImportResultDto` carries `committed`, `loungeId`, `added` / `reactivated` / `skipped` (rows: `line`, `ruleId`, `ruleKey`, `ruleKeyReadable`, `description`), `inactiveInFile` (lines) and `invalid` (`{ line, errors[] }` — every error on the row). The import routes take a body up to 3 MB (the CSV inside JSON); every other route keeps Express's 100 KB. Controllers validate body shape and throw `ErrorResponse(msg, 400)` on bad input; the service throws `ErrorResponse(…, 404)` for a missing host.

## 6. Client state model

`store/appStore.ts` is the single Zustand store, composed with the Zustand **slices pattern**: one store and one `useAppStore` hook, but each feature's state + actions live in `store/slices/<name>Slice.ts` and are typed in `store/types.ts` (`AppState` = the intersection of the slice interfaces). Slices reach each other through `get()` (a scan calls `refreshEntries`; an approval calls `reset`). It holds, in one object:

- **View and role** — `view` (the `App.tsx` switch, no router; the vocabulary `View` is defined once in `lib/views.ts`: `scanning` | `entries` | `rules` | `globalRules` | `clubs` | `lounges` | `approvers`; the rules and clubs views load the clubs; the global-rules view re-reads its rules on every visit, since they decide every scan) and `role` (`lib/role.ts`: `operator` | `admin`, the temporary "View as" switch until login — read from and written to `localStorage`, default `operator`). `lib/role.VIEWS_BY_ROLE` says which pages a role may open (the operator: Scanning only, with no navigation; the admin: every page, in its tab order), and `setView` sends a page the role can't open to Scanning, as `setRole` does when the new role can't see the current page. **Scanning** (for both roles) has two tabs, local to `App.tsx`'s `ScanningView`: **Scanning** (`ScanStage`: the scan box and ⚡ Manual approval; then `RecentScans`) and **Entries** (the operator's log, `EntriesTable` with `groupByDay`). **All entries** (`entries`, the admin's full log) is the same `EntriesTable` with `withAdminTools`, and the two pages share one filter state; opening Scanning applies the pure `lib/entryFilters.scanningFilters(filters, stationLounge)` — it keeps All lounges or the station's lounge (its lounge switch has only those two; any other choice becomes the station's lounge, or All lounges while the station has none), the search and one result, clears every filter it has no control for and goes back to whole parties, and reloads the log only when that changed something. The redesigned screens are drawn with Tailwind on shadcn components (`components/ui/`, added with the shadcn CLI: `table`, `tabs`, `badge`, `input`, `toggle-group`) inside a `data-tailwind` wrapper, which keeps `styles.css`'s POC button rules off them. The desk's windows (the scan flow's steps and the exception form) share one shape, `components/DeskModal.tsx`: a title bar, a body that scrolls inside the window, and a footer bar with the grey actions on the left and the one blue action on the right; a modal scan field (`ScanField`) is a form spanning that body and footer. Both pages mount the same modals (`EntryModals` in `App.tsx`). Hiding the admin pages and the export is screen-only until login: the server checks no role yet. The view slice also holds **`theme`** (`lib/theme.ts`: `system` | `light` | `dark`, read from and written to `localStorage` as `jetlog.theme`, default `system`) and `setTheme`; `main.tsx` puts the resolved theme on `<html>` before the first render (no flash, and no inline script), and `hooks/useApplyTheme` keeps it in step after — including a system change while the choice is `system`. The header's toggle sets the opposite of the theme on screen as an explicit choice. It also holds **`language`** (`lib/language.ts`: `he` | `en`, read from and written to `localStorage` as `jetlog.language`, default `he`) and `setLanguage`; `main.tsx` puts `lang` on `<html>` and starts i18next (`i18n/index.ts`) in that language before the first render, and `hooks/useApplyLanguage` keeps both in step after. **The layout never mirrors:** `<html>` is always `dir="ltr"`, so the header, tabs, table columns, forms and window footers keep the English order in Hebrew. Each piece of text reads in its own direction instead: one rule in `index.css` gives every element that holds only text `unicode-bidi: plaintext`, so it takes its direction (and its `text-align: start`) from its first letter — a Hebrew label reads right to left at the right of its box, a code left to right. It sets no `direction`, so flex, grid and table order never change. The scan fields are always left to right (`.scan-input`). A few rules in `index.css` apply only in Hebrew (`:lang(he)`), on every page: the boxes people type in (text boxes, multi-line boxes, form dropdowns — not the scan fields) are fully right to left, the cursor included; a field's value (`dd`) sits at the right under its label; a form's label row (name, `*`, counter) reads right to left; a window title keeps clear of the × in the top-right corner; a deny reason's bullet sits at its right. Look there first when something reads oddly in Hebrew.
- **Scan flow** — `mode: 'scan' | 'club' | 'result' | 'guest'` (`'club'` = the club question, with `clubPrompt: { rawBarcode, options }` — the options are asked for the station's lounge; nothing logged yet; `chooseClub(id | null)` posts the scan once, `reset()` cancels; if the options call fails the scan is posted without a club), `busy`, `error`, `primary` (last `ScanResponse`), `lastScanRaw` (for "approve anyway"). **On screen, `mode` is a modal:** `'scan'` = no modal (the page at rest: the main scan box and the log); every other mode is a step of one flow modal (`ScanFlowModal`), and the pure `lib/scanFlowStep.ts` adds the `error` step (a primary scan that failed, from rest or from a result) and steps aside while the exception form or an entry's details are open — **one modal at a time**: a modal opened from another replaces it, and closing it brings the first back (the result stays in `primary` meanwhile). `error` is not cleared when a scan starts, only when its answer arrives, so a failed scan's modal doesn't blink shut during the retry. `scanPrimary` also runs from the result's own "Scan the next passenger" field: the new answer replaces the result.
- **Guest session** — `guest: { hostEntryId, total, results, fromEntryId }`, `lastGuest`. `total` = places to fill: done when the APPROVED results reach it (a denied guest holds none; the server enforces the same count). `startGuestsFor(host)` reopens a host the rules approved from its details window with its places left (a host approved by exception has none): the guest loop replaces that window, without switching the view, and `fromEntryId` remembers the host; `endGuests()` ends the loop (the guests scanned stay logged) and reopens that host's details, fetched fresh. Each guest scan re-posts with `hostEntryId`.
- **Entries** — `entries` (the pages loaded so far, newest first), `entriesNextCursor` (null = all loaded), `entriesTotalHosts` (from the first page), `entriesLoadingMore`; `refreshEntries(MERGE | RESET)` and `loadMoreEntries()` combine pages through the pure `lib/entriesPaging.ts` — MERGE (after a scan or a modification) puts a fresh first page on top and keeps the older pages and their cursor, RESET (new filters, a lounge/club re-code) starts again; `replaceEntryGroup` puts a modified party in place wherever it is loaded. The table's footer loads the next page on scroll (`hooks/useInfiniteScroll`), with **Load more** as the fallback. `entryFilters` (the server-side filters of the log and the export, `lib/entryFilters.EntryFilterValues`: changing one resets the log — it is paged, so filtering client-side would see only the loaded pages — except the match mode, which only changes what the screen hides), `entriesError` (why the log couldn't load, shown at the filters with the server's parameter names turned into screen labels by `lib/entryFilters.readableFilterError`; a refused filter — a 400 `ApiError` from `api/client.ts` — also empties the log, so old rows never pass for its result, while a network or server failure keeps them), `searchQuery` (screen only, not in the export), `sortKey`, `sortDir`, `exporting` / `exportError` (`exportEntries()` returns the file; the component saves it), `selectedEntry` (details modal), and **`recentScans`** (the Scanning page's Recent strip: the 6 latest hosts at the station's lounge from their own request, `refreshRecentScans()`, so the log's filters never narrow it; re-read with every MERGE refresh — after a scan, an exception, a change — and when the station's lounge changes; empty while the station has none; a failure keeps the strip). In single-entries mode `lib/entriesView` hides the rows the server marked `matchesFilters: false` (a host stays as a dimmed context row above a guest that matched).
- **Exception form** — `exceptionOpen`, `exceptionRaw`, `exceptionEntryId` (set by a result card's "Approve anyway": the scanned entry is approved **in place** through `POST /api/entries/:id/exception` — one entry, never a second; null = a manual approval with no barcode, which logs a new entry through `POST /api/scan/exception`), `submittingException`. The form sends a `quantity` (1 to the `max_exception_quantity` global rule, read from the loaded global rules by `lib/exceptionQuantity.ts`); a successful approval goes back to a fresh scan screen, never to a guest step. "Approve anyway" is not offered when the pass is already admitted (`lib/entryActions.offersApproveAnyway`) — the result there offers **Re-enter (flight delay)** instead. A re-entry reuses this same form through `exceptionReentry` + `openReentry(raw)`: it posts to `POST /api/scan/reentry`, always carries the scanned barcode, hides the quantity (always 1), and the log shows it with a `⚡ Re-entry` badge.
- **Entry edit** (`entryEditSlice`) — modifying the entry open in the details window (`selectedEntry`): `entryBusy`, `entryError` (shown in the window), `entryRefusal` (a refused move's lounge and reasons, so an exception can still move it), `entryClubPrompt` (a move or rescan waiting for a club pick — "ask first, change once"). `moveEntry` / `rescanEntry` / `chooseEntryClub` / `approveEntryAsException` / `voidEntry` / `changeEntryQuantity` return an `ActionResult` (null = ignored or a prompt opened); a change shows the entry as it is now (`pickChangedEntry` from its returned group) and refreshes the log. `openEntry(id)` (entries slice) fetches one entry — "Open their entry" after `ALREADY_ENTERED`, the guest loop's return to its host — and returns an `ActionResult`: a failure is shown as a toast (`useScanFlow`), never written to the flow's `error`, which would read as a failed scan.
- **Rules editor** — rules carry `loungeId` (null = all lounges): the editor picks it (active lounges, plus the rule's current one) and the list filters by it, client-side; people see `ruleKeyReadable`, never the id-based `ruleKey`. `rulesList`, `rulesLoading`, `editorRule`, `editorId` (null = create/duplicate → POST; set = edit → PATCH), `savingRule`, `ruleError`. Bulk and import: `bulkRulesBusy` with `setRulesActive(ids, active)` / `deleteRules(ids)`, and `rulesImportBusy` with `previewRulesImport(csv, loungeId)` / `importRules(csv, loungeId)`. These return an `ActionResult` (`{ ok, data }` or `{ ok: false, error }`; `null` = ignored, one already in flight) instead of writing `ruleError`, because the page shows the outcome in a toast (shadcn Sonner, mounted once in `App.tsx`) or the import dialog. Each refuses a selection or file over the limits before posting, and re-reads the list after a successful write. The selection itself (rule ids), the filters and the import dialog's file, target and preview are component state in `RulesPage` / `RulesImportDialog`; a filter change clears the selection.
- **Approvers** — `approvers` (loaded once on mount for the exception dropdown, filtered to `active` via `lib/approversView.ts`), `approversLoading`, and the admin-view slice `approverEditor`/`approverEditorId` (null = create → POST; set = edit → PATCH), `savingApprover`, `togglingApproverId` (row whose deactivate/reactivate is in flight), `approverError`.
- **Clubs** — `clubs` (loaded by the rules and clubs views — the rule editor's club dropdown offers the active ones plus the rule's current club), `clubsLoading`, and the admin-view fields `clubEditor`/`clubEditorId`, `savingClub`, `togglingClubId`, `clubImageBusyId` (image upload/removal in flight), `clubError`. A code change re-reads the rules (their keys spell it) and the log.
- **Global rules** — `globalRules` (the fixed keys and their values), `globalRulesLoading`, `savingGlobalRuleKey` (one save at a time — the key whose PATCH is in flight), `globalRuleError` (shown on the page, e.g. the server's 400 for an invalid value). `saveGlobalRule(key, value)` PATCHes one value, then re-reads the list so the page shows the stored, normalized form; unsaved drafts live in the page component, not the store.
- **Lounges** — `stationLounge` (this station's lounge **id**, read from and written to `localStorage` via `lib/stationLounge.ts` — a saved value that isn't a positive integer, e.g. a code saved before lounges were referenced by id, reads as "not picked"; `null` until picked — the Scanning page shows a picker instead of the scan input, and scan/exception actions refuse to post), `lounges` (loaded on mount), `loungesLoading`, and the admin-view fields `loungeEditor`/`loungeEditorId`, `savingLounge`, `togglingLoungeId`, `loungeError`. After each load a remembered lounge that is no longer active is forgotten (the station is asked again). When the station's lounge changes (picked, or forgotten), a log on the old station lounge follows it (`lib/entryFilters.stationLoungeFollowed`; All lounges when there is none) and the Recent strip is re-read. A lounge's code is just a label: stations and the filter hold its id, so a code change never touches them — saving one only re-reads the log, whose codes are joined at read time.

Actions live in the store and own the async flow (set `busy` → call `api` → apply → `refreshEntries`). Every async action keeps these invariants (each is covered by `store/slices/*.test.ts`):

- **One at a time.** A scan, save, submit or toggle already in flight makes a repeat call a no-op (`busy` / `saving*` / `submittingException` / `togglingApproverId`), so a double Enter from the wedge can't post a pass twice.
- **Flags always released.** In-flight flags are cleared on success *and* failure (`finally`).
- **Latest wins.** Overlapping loads (`refreshEntries`, rules, approvers) take a ticket from `createLatest()` (`store/latest.ts`); only the newest may write. `reset()` also invalidates in-flight scans, so a response that lands after the operator left that flow is dropped (the entry is still logged; the refresh shows it). `loadRules`/`loadApprovers` dedupe UI-triggered loads; a save re-reads the list *after* its write rather than joining an older load.
- **Errors are visible, in the screen's language.** Every slice's error (`error`, `entriesError`, `exportError`, `entryError`, `ruleError`, `approverError`, `loungeError`, `clubError`, `globalRuleError`, and a failed `ActionResult`) is a `Message` (`lib/message.ts`), made by `lib/errors.toMessage`: the server's own words as they are (English), or one of our catalog keys — the server couldn't be reached (`error.network`), answered without words (`error.requestFailed`), or the action's fallback (`error.scanFailed`…). Components show them through `useMessageText`. A slice's error shows in its modal when open, otherwise on its page (`RulesPage`, `ApproversPage`). The Scanning page has no page banner: a failed primary scan is the flow modal's error step, the club question and the guest loop show their own failure, and the exception form shows the flow `error` itself (`closeException` clears it, so cancelling returns to the result, not to an error).
- **The scanner's keystrokes reach a scan field the operator sees.** The scanner is a keyboard wedge. On the entries pages (Scanning and All entries) `hooks/useWedgeRouting.ts` applies the pure `lib/wedge.ts`: a printable key while focus is on a row, a button or the page moves focus to the open modal's scan field (`data-scan-field`), or the main scan box with none open, before the key types — on All entries, and on the Scanning page's Entries tab, which have no scan box, a scan with no modal open is swallowed through its Enter, with a message pointing to Scanning (or to its Scanning tab); a text field keeps its typing (and, with no modal, a dropdown); in a modal with no scan field the scan is swallowed through its Enter, so it presses nothing; a scan while the field is busy with the last one is swallowed too, with a message (never queued: it could land in the wrong step). Forms that change data (the exception form, the details window's approve-as-exception, quantity and void panels) take `blockEnterSubmit` (pure check `lib/wedge.isEnterSubmit`): Enter in a text box doesn't submit them, only their button does. Every modal focuses its scan field when it opens, and a closing modal gives focus back to the main scan box unless another modal is open.

The store is tested without React: `store/testing.ts`'s `makeStore()` builds a fresh isolated store from the exported `createAppState` (`zustand/vanilla`), with `api/client.js` mocked. Components never call `api` directly; they read through `useScanFlow` / `useEntriesView`, which combine store slices with the pure logic in `lib/entriesView.ts`. The entries table owns its own data lifecycle (`useEntriesView` refreshes on mount).

## 7. Extension points

**Add a rule dimension** (e.g. a new matchable field):
1. Add the column to `rules` in `db/schema.ts`; `npm run db:generate`, review, migrate.
2. Add it to `RuleLike`/`ScanDimensions` in `domain/types.ts`, to the `DIMENSIONS` list and the key's part order in `domain/ruleKey.ts` (`ruleKeyFromDimensions`, `buildRuleKey`, `readableRuleKey`), and to `rules.json`; a migration recomputes every stored `rule_key`.
3. Populate it in `domain/parseBoardingPass` if it comes from the barcode; otherwise collect it from the operator.
4. Thread it through `RuleDto`/`RuleInput` (server + client mirror) and `RuleForm`.

**Add a global scan rule** (a check every scan must pass):
1. Add its key to `GlobalRuleKey` in `domain/globalRules.ts`, its validation to `normalizeGlobalRuleValue`, its typed field to `GlobalRulesConfig`/`parseGlobalRules`, and its check (with a new `GlobalRuleFailure`) to `checkGlobalRules` — test-first.
2. Ship a migration that inserts its row with the default value, in the same change (`parseGlobalRules` fails closed without it).
3. Add the new reason to `DenyReason` and its place in `DENY_REASON_ORDER` (`domain/denyReasons.ts`), and mirror it in the client.

**Add an endpoint:** route in `routes/` → controller in `controllers/` (a plain `async` handler — Express 5 forwards rejections; validate shape, `@desc/@route/@access` header, return the envelope) → service in `services/` (business rules + DB) → DTO in `types/dto.ts`, mirrored in `client/src/api/types.ts` and a function in `client/src/api/client.ts`.

**Add a destructive script** (anything that deletes or replaces data — a reset, a reimport): read the lock with `readLockState` (`db/seed.ts`) and refuse through a pure decision in `db/seedGuard.ts`, tested like `decideSeed` — inside the transaction that does the damage, not only up front. Never add an unlock path to code.

**Add a store slice:** declare its interface in `store/types.ts` and add it to `AppState`; implement `create<Name>Slice: SliceCreator<…>` in `store/slices/`; spread it into `createAppState` in `store/appStore.ts`; expose it through a hook if a component needs many fields; keep pure logic in `lib/`. Tests go in `slices/<name>Slice.test.ts` (the **store-test-writer** agent owns them).

**Add a string** (any text a person reads): put it in `client/src/i18n/en.json` and, with its Hebrew, in `he.json`, under the same key (a section per screen or feature: `header.*`, `view.*`…); read it with `useTranslation().t('section.key')` in a component, or `i18n.t` outside React. The keys are typed from `en.json`, so a typo fails the build. Values are `{{name}}`, plurals i18next's `_one`/`_other` (Hebrew adds `_two`). Render a sentence as **one** string in an element of its own: a Hebrew sentence split across elements, or with markup inside, reads in the wrong order (give such an element `dir="auto"`); a code inside Hebrew text goes in `Ltr`. A string only on an admin page may wait for its Hebrew: list its key in `i18n/he.pending.json` instead, until the admin pages get their Hebrew (planned). The key test fails on a key missing from either catalog, a pending key that has Hebrew, and a `{{value}}` one language lacks. New Hebrew is a draft until Mark or IsraJet review it: `npm run i18n:drafts` counts the drafts and writes the review sheet, and a reviewed key goes into `he.reviewed.json`. `lib/` never imports the catalogs: a pure function returns a key (with its values) and the component translates it. Server error messages are English sentences and are shown as they come.

**Change the look** — the design tokens in `client/src/index.css` are **the one place**. Colours are shadcn tokens (`--background`, `--card`, `--primary`, `--muted-foreground`, `--success`, `--destructive`, `--exceptional`, `--warning`, `--header`…), each surface with its `-foreground`, defined under `:root` (light) and `.dark` (dark). To add one, the shadcn way: define it in both blocks, then expose it in `@theme inline` (`--color-x: var(--x)`) for `bg-x` / `text-x`. Fonts are `--font-sans` / `--font-mono`, radius is shadcn's `--radius` scale, spacing is Tailwind's `--spacing` base, and the `nav` breakpoint folds the admin tabs. Never write a raw colour in a component or in `styles.css`: soft tints are mixed from a token (`bg-success/10`, or `color-mix(in oklch, var(--success) 12%, transparent)` in plain CSS). New UI is Tailwind utilities + shadcn components inside a `data-tailwind` element; `styles.css` is the POC styling, unlayered (it beats Tailwind's layers), and shrinks as each screen is redesigned.
