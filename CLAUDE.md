# JetLog — IsraJet lounge-entry system

Scan boarding pass → parse BCBP → match entry rule → handle guests → log entry → show result.

This **started as a POC and is now the real application** heading to production on IsraJet's own on-prem machines. Treat it as a product, not a demo. The POC-era docs are kept as history only (see "Read first").

## Stack (as-is)
- `server/` — Node + Express + **TypeScript** (ESM, strict) · **Drizzle ORM → PostgreSQL** · Vitest + supertest
- `client/` — Vite + React 18 + TypeScript · **Zustand (one store, split into slices under `store/slices/`)** · **Tailwind v4 + shadcn/ui**, with one set of design tokens in `client/src/index.css` (shadcn names, light `:root` + `.dark`) — the one place to change the look; `styles.css` is the POC styling, replaced screen by screen
- Server layering: `routes/` wire → `controllers/` HTTP (validate, envelope) → `services/` business rules + DB → `domain/` **pure, no I/O**. No SQL in controllers; `domain/` never imports `db/`.
- Client layering: `lib/` pure logic → `hooks/` store wiring → `components/` render only. `App.tsx` is a view switch (`scanning` | `entries` | `rules` | `globalRules` | `clubs` | `lounges` | `approvers`, from `lib/views.ts`), offered per role (`lib/role.ts`: `operator` | `admin`, a temporary "View as" switch until login); no router.
- Response envelope everywhere: `{ success: true, data }` / `{ success: false, error }` via the central `errorHandler` (controllers are plain `async` handlers — Express 5 forwards rejected promises to it).

## What exists today
- **Scan pipeline** (`services/scanService.ts`): parse → **every check runs** (global rules, dedup `uniq_key`, wildcard-collapse rule match or the guest policy) → **every scan is logged**, approved or not, with **every** deny reason (`reasons` in the response, `entries.deny_reasons` `text[]` on the row, one pinned order in `domain/denyReasons.ts`). The club picker comes last: offered only when every other check passes; `CLUB_REQUIRED` when the club alone fails.
- **Global scan rules** — a `global_rules` table of fixed keys with string values (`departure_airports`, `max_days_before_departure`, `max_days_after_departure` — and two operator rules scans never check: `max_hours_to_modify_entry` (`0017`, `48`) and `max_exception_quantity` (`0020`, `1000`, at most 10,000); the three scan rules seeded `TLV`/`2`/`2` by migration `0013`; rows only ever added by a migration), checked by the pure `domain/globalRules.ts` on every scan, guests included, before anything else: wrong airport, unknown date, too far ahead, too long ago — each its own deny reason. Days counted from today in Israel, inclusive, with the flight's year taken as whichever is nearest today. Exceptional approval skips them. The admin edits values in a `Global rules` view (one row at a time) via `PATCH /api/global-rules/:key` (validated per key).
- **Guest flow** with a per-rule `guest_policy`: `ANY` · `SAME_CARRIER` · `SAME_FLIGHT` (a strictness hierarchy → one value; `ANY` is explicit, `NOT NULL DEFAULT 'ANY'`). It is snapshotted onto the host entry at admission so a mid-session rule edit can't change that host's guests.
- **Exceptional (manual) approval** — failed scan or no barcode; approver (validated against the DB `approvers` table) required, notes optional; a group is **one entry with a `quantity`** (1 to the `max_exception_quantity` global rule, at most 10,000; default 1, changeable later inside the modify window). An exceptional entry has no guests: **guests belong only to a host the rules approved**, up to its rule's allowance, and a guest the rules refuse can't be approved as an exception.
- **Modifying an entry in place** (`services/entryModificationService.ts`, pure checks in `domain/entryModification.ts`) — within the modify window (global rule `max_hours_to_modify_entry`, 48 h from creation): move a host to another lounge (re-checked there; its guests move and are re-checked), rescan a denied/garbage entry (any readable pass; dedup still applies), approve a denied host or a refused move as an exception (reasons kept; never a guest), change an exceptional entry's quantity, void an approved entry scanned by mistake (reason + approver; guests too). No audit trail — `modified_at` only. The server enforces each host's guest places (`entries.allowed_guests` − approved guests).
- **Invalid-scan handling** — virtual `isValidBcbp` (computed on read, never stored); garbage rows hidden behind a chip; per-row details modal.
- **Rules editor** — list/search, create/edit/duplicate, deactivate, bulk (de)activate and bulk delete of **inactive** rules (all or nothing), CSV export and **CSV import** (preview, then all rows or none; only adds — skips a key an active rule holds, reactivates an identical inactive rule; the admin picks the target lounge, or all lounges); `rule_key` is auto-derived on save; **no two ACTIVE rules may share a `rule_key`** (409, enforced by a partial unique index).
- **Approvers admin** — DB-backed `approvers` view: list/search, create (internal/external + company), edit, deactivate/reactivate; the exceptional-approval dropdown reads the active ones.
- **Multi-lounge** — DB-backed `lounges` (unique editable `code` — no name — optional `description`, `active`); each station picks its lounge once (store + `localStorage`) and every scan/exception sends it (**required**; unknown/inactive → 400); a `lounges` admin view (list/search, create, edit incl. re-code, deactivate/reactivate).
- **Rules per lounge** — `rules.lounge_id` (NULL = all lounges; every seeded rule). A scan uses its station's own lounge rules first, then the all-lounges ones; a lounge where no rule applies denies. Rule keys spell **ids** — `carrier-compartment-ff-companyVar-<club id|#>-<lounge id|#>`, stored when the rule is written — so a re-code changes no key; `ruleKeyReadable` (computed on read, never stored) spells them with codes for people.
- **Clubs** — DB-backed **global** `clubs` (unique editable `code`, optional `description`, `active`, a resized WebP `image` stored in the row). The club isn't in the barcode: before logging a primary scan the client asks `POST /api/scan/club-options` (logs nothing; takes the station's `loungeId`) and the operator picks one of the clubs an active rule for that pass uses, or None (a club-less passenger: `entries.club_id` NULL). Rules reference clubs by id (`rules.club_id`, NULL = any club or none). The Excel's `Guest` "club" is retired (guests use `is_guest` + `host_entry_id`).
- **Roles (until login)** — a temporary **View as: Operator / Admin** switch in the header, remembered per computer (default Operator). The operator sees only **Scanning**: two tabs, **Scanning** (the scan box, ⚡ Manual approval, and **Recent** — the 6 latest scans at the station's lounge) and **Entries** (the log grouped by scan day, its toolbar on screen while scrolling: the lounge switch — the station's lounge or all — result and search); the admin gets tabs: Scanning, **All entries** (the full log: filter panel, parties switch, export), Rules, Global rules, Clubs, Lounges, Approvers. Screen-only: the server checks no role yet.
- **Hebrew and English** — i18next with `client/src/i18n/en.json` + `he.json`; Hebrew by default, a header switch remembered per computer (`jetlog.language`), `<html lang>` from the language. **Nothing mirrors:** `<html>` stays `dir="ltr"` and the layout is the English one; each text-only element reads in the direction of its first letter (`index.css`), codes kept LTR (`Ltr`). Hebrew comes first for the operator's screens; admin-only strings may wait in `he.pending.json`. All Hebrew is a draft until reviewed (`he.reviewed.json`, `npm run i18n:drafts`). Scan fields type the US-layout character for each key, so the scanner works with a Hebrew keyboard layout.
- **Entries table** — the hosts with guests nested, paged from the server (100 hosts a page, keyset cursor), a filter bar (lounge, result, search — screen only), a filter panel with every server-side filter, a Whole parties / Single entries switch (ⓘ tooltip), Export CSV, sort.
- **The rule at scan time** — a scan, rescan or move stores the matched rule's key (ids), its readable key with the codes of that moment, its description and its comments on the entry; a later rule edit or re-code changes none of them (a deliberate exception to "compute what people read"). No matched rule, no key: `rule_key` and the three are null, and always null on guests. Rules carry optional `comments` (the rules API and the CSV import, where the column is optional).
- **Entries filters and export** — one filter vocabulary (`domain/entryFilters.ts`: lounge, club, airline, class, frequent flyer, flight-date and scan-date ranges, status incl. voided, host/guest, exceptional, modified, deny reason) for the log (`GET /api/entries`) and an Excel-friendly CSV export (`GET /api/entries/export`, `domain/entriesCsv.ts`, with the raw barcode — personal data — and the rule at scan time, streamed in batches, refused above 500,000 rows — about two years). Filters select **whole parties** (a host and its guests travel together); `match=entry` makes the export strict, and `matchesFilters` on each log row says which rows matched.

## Database
- `rules` (+ `comments`; `description` and `comments` ≤ 2,000 characters; `guest_policy`, `club_id` → `clubs.id`, NULL = any club, `lounge_id` → `lounges.id`, NULL = all lounges; `rule_key` spells ids), `entries` (+ `frequent_flyer`, `frequent_flyer_number`, `guest_policy` (host-admission snapshot), `deny_reasons` (`text[]`, null = none recorded), `readable_rule_key_at_scan_time` / `rule_description_at_scan_time` / `rule_comments_at_scan_time` (the matched rule as it read at scan time — stored, never recomputed; null when no rule matched or on a guest), `is_exceptional`, `quantity` (1 to the `max_exception_quantity` global rule on a host approved by exception, checked by the code; else 1 — a DB check), `approver_name`, `exception_notes`, `order_number`, `service_company`; `raw_barcode`/`uniq_key` nullable), `approvers` (`name` globally unique, `kind` internal/external, `company`, `active`), and `lounges` (`code` unique + editable, `description`, `active`; `entries.lounge_id` is an FK to `lounges.id`), and `clubs` (`code` unique + editable, `description`, `active`, `image` bytea, `image_hash`; `entries.club_id` → `clubs.id`, NULL = club-less), and `deployment_state` (one row: the **go-live lock** — `locked`, `locked_at`, `locked_by`), and `global_rules` (`key` unique, `value` text, `updated_at`). **Foreign keys always reference `id`, never a code.** **`server/src/db/schema.ts` is the model — one file, all tables.**
- Migrations `0000`–`0020` in `server/src/db/migrations/`, **generated by `drizzle-kit generate`** (`0004` is a `--custom` backfill; `0005` adds the `entries` dedup + created_at indexes; `0006` makes `rules.guest_policy` NOT NULL default `'ANY'` and adds `entries.guest_policy`; `0007` adds the `approvers` table; `0008` adds `lounges`, seeds lounge `A` in the migration, and makes `entries.lounge` its FK; `0009` moves that FK to `entries.lounge_id → lounges.id` with a backfill, and drops `lounges.name`; `0010` adds `clubs` (seeded with 15 codes), `rules.club_id`/`entries.club_id`, retires the 40 Guest rules and drops the text `rules.club`; `0011` adds `deployment_state`; `0012` (`--custom`) inserts its one unlocked row; `0013` adds `global_rules` and inserts its three rows; `0014` adds `entries.deny_reasons`; `0015` adds `rules.lounge_id` and recomputes every `rule_key` from ids; `0016` adds the partial unique index `rules_one_active_per_rule_key`; `0017` adds `entries.allowed_guests`, `modified_at` and the void fields, and inserts the `max_hours_to_modify_entry` global rule; `0018` adds the `entries` host and flight-date indexes; `0019` adds `rules.comments`, limits `description` to 2,000 characters, and adds the three at-scan-time `entries` columns, backfilled from the active rules; `0020` adds `entries.quantity` with its check and inserts the `max_exception_quantity` global rule); hand-edit the SQL only to add data backfills. Seed = the clubs the rules use via `seedClubs` (non-destructive) + 231 rules from the Excel (`seed-data/rules.json`, reseed-safe; readable club and lounge codes — `#` = any / all — mapped to ids, and each key derived from them) + the base approvers via `seedApprovers` (non-destructive). **The seed data is not final:** `rules.json` (and the club codes derived from it) will change as Vlad reviews the rules — treat it as the current transcription, not a fixed spec. **`db:seed` is guarded (`db/seedGuard.ts`):** it seeds an empty rules table and quietly skips a non-empty one; replacing needs `--force` (a dev reseed drops rules added by hand), `NODE_ENV=production` refuses even that, and a **locked** database (`npm run db:lock`, at go-live) refuses everything — `seedRules` re-checks inside its transaction. Production runs migrate only; see [docs/DEPLOY.md](../jetlog/docs/DEPLOY.md).

## Governing decisions (in force — log a `/decision` before changing any)
- **ORM stays Drizzle.** `schema.ts` is the visible model; `drizzle-kit generate` is Alembic-style auto-generated migrations. Do **not** introduce Sequelize (and never `sync()`-style auto-DDL).
- **Input is the USB scanner (keyboard wedge) only.** Camera/photo scanning has been **removed**.
- **One component library** for the admin/RTL work — settle **shadcn vs MUI first** (recommended: shadcn). Never both.
- **Deploy = docker-compose on 2 on-prem machines over VPN**, via GitHub Actions or a script. No Terraform, no cloud. **One compose file per VM:** the DB VM runs Postgres only (`deploy/db/`), and the app VM runs api + web with no pg (its deploy is planned). Production runs **migrate only**; the database is seeded once while empty and **locked** at go-live (`deployment_state`). Runbook: [docs/DEPLOY.md](../jetlog/docs/DEPLOY.md).
- **Approvers are a DB table** (`approvers`) with a CRUD API; the admin panel will manage them. **Guest policies stay a string vocabulary** in `domain/` (not a table) — tabling deferred indefinitely.
- **Every deny reason is reported and stored** (this reversed the earlier rule "deny reason lives in the response, not on the row"): the response's `reasons` array and `entries.deny_reasons` hold the same list, in the order pinned in `domain/denyReasons.ts`.

## Safety rules (hard — these have bitten us)
- **Never run integration tests against a live DB.** `npm test` is unit-only by default. Integration needs a **dedicated** `TEST_DATABASE_URL` (refused if it equals `DATABASE_URL`): `npm run test:integration`.
- **Mark runs `npm run db:generate` and `npm run db:migrate` himself — agents never run them.** The agent edits `schema.ts`, hands Mark the `db:generate` command, hand-edits the generated SQL only to add a seed/backfill, then hands him the `db:migrate` command with the row-count check to run before/after.
- Migrations against the dev DB: additive only; check row counts before/after. **Never delete data you didn't create.**
- **Production (DB VM SQL.Layam 192.168.1.1, `deploy/db/`):** Mark runs every command there himself, from his laptop over VPN + SSH tunnel ([docs/DEPLOY.md](../jetlog/docs/DEPLOY.md)). Agents never connect to it, never print/commit its secrets (`.env.prod` is git-ignored), never point tests at it, and never add an unlock path for `deployment_state` to code.
- Don't commit anything user-facing or schema-changing without Mark's go. Stage only your own files — Mark keeps WIP in the working tree.
- **Never modify or push `../israjet-launges`** (the pre-split archive). Read it only.
- **Never write a mention of jetlog-ops, the agents, the skills or Mark into a jetlog file** (code, comments, README, DEPLOY.md, USER_GUIDE.md, workflows).

## Workflow
- **Server first, then client — each handed to Mark for review before the next starts.** A task that spans both is built in two stops: (1) the server — schema, then services/controllers/endpoints with their tests — then **stop and hand it to Mark to check**; (2) only after he's checked it, the client — then **stop and hand it to Mark to check** again. Never build the client before the server has been reviewed.
- Branches, the same names in both repos: `main` · `staging` (demo-safe snapshot) · `feature/*` off `staging`. The POC's `feat/phase-1…6` branches exist only in `../israjet-launges`.
- Small, topical commits with **descriptive messages** — Mark studies the history; the message is the "why". Commit with `/commit`, only after Mark's go.
- Quality gate before any PR: `/verify`. Scope/approach changes → `/decision`, which appends to **`../jetlog-ops/docs/DECISIONS.md`** (the POC-era log in `../jetlog-ops/docs/archive/` is frozen).
- **New features ship with tests that prove them; pure domain logic is written test-first.** Not a rebuild of what exists — the rule is for new work.
- **Any change under `client/src/store/` goes through the `store-test-writer` agent** before review — it adds/updates the slice tests and proves they can fail.
- **Any user-visible change goes through the `user-guide-writer` agent** before review — a new or changed screen, flow, button, label, message, deny reason, rule behaviour or limit. It updates [docs/USER_GUIDE.md](../jetlog/docs/USER_GUIDE.md) (and its screenshot shot list) in the **same commit** as the change (both are in jetlog).
- **Keep [../jetlog-ops/docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) current.** When a change touches the module dependency rules, the request lifecycle, the data model or its invariants, the API contract, the client state model, or the extension points, update it in the **paired commit** (`/commit`: the code in jetlog, ARCHITECTURE.md in jetlog-ops, same branch and message). A routine change that only follows the existing patterns needs no edit there. The same goes for a task's status line in `../jetlog-ops/docs/PLAN.md`.
- **Keep [docs/DEPLOY.md](../jetlog/docs/DEPLOY.md) current.** It is the production runbook Mark follows on the servers, so a stale command there runs against production. When a change touches `deploy/`, a migration, the `db:*` scripts, the Dockerfiles or compose files, environment variables or secrets, ports, or the expected row counts, update it in the **same commit**. Check that every DEPLOY.md command still matches the code.
